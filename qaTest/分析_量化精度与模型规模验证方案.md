## 一、量化精度验证

### 1.1 llama.cpp GGUF 支持的量化级别

| 量化类型 | bits/weight | 大小(vs FP16) | 质量 | 解量化方式 | 解量化开销 |
|---------|------------|--------------|------|-----------|-----------|
| Q2_K | 2.56 | ~16% | 低 | K-quant unpack | 高（复杂位操作） |
| Q3_K_M | 3.35 | ~21% | 中低 | K-quant unpack | 中高 |
| Q3_K_L | 3.35 | ~21% | 中低 | K-quant unpack | 中高 |
| **Q4_0** | **4.0** | **~25%** | **中** | **对称均匀量化** | **低（scale+bias查表）** |
| Q4_K_M | 4.5 | ~28% | 中 | K-quant unpack | 中 |
| Q4_K_S | 4.5 | ~28% | 中 | K-quant unpack | 中 |
| Q5_0 | 5.0 | ~31% | 中高 | 对称均匀量化 | 低 |
| Q5_K_M | 5.5 | ~34% | 中高 | K-quant unpack | 中 |
| **Q6_K** | **6.6** | **~41%** | **高** | **K-quant unpack** | **中低** |
| **Q8_0** | **8.0** | **~50%** | **很高** | **8bit截断→FP16** | **低（简单截断）** |
| FP16 | 16.0 | 100% | 基准 | 无需解量化 | 无 |

**关键区分**：
- `Q*_0` 系列（Q4_0, Q5_0, Q8_0）：**均匀量化**，每个 block 统一 scale。解量化 = 查表 + 乘法，CUDA kernel 友好
- `Q*_K*` 系列（Q4_K_M, Q5_K_M, Q6_K）：**K-quant**，每个 superblock 有可变精度。质量更高但解量化需要位操作 unpack

### 1.2 Orin 端侧解量化开销分析

Orin 硬件特点：
- 2048 CUDA cores + 64 Tensor cores
- 12-core ARM Cortex-A78AE
- 2x NVDLA v2.0（Deep Learning Accelerator）
- 内存带宽：204.8 GB/s（Orin AGX 64GB）

**llama.cpp 在 Orin 上的推理路径**：

```
GGUF 权重 → CUDA kernel 解量化 → FP16 matmul → 输出
            ↑__ 解量化与matmul融合在同一个kernel中，不是独立步骤
```

**解量化开销的实际影响**：

| 量化类型 | 内存带宽压力 | 解量化计算 | 瓶颈在哪 | 推荐度 |
|---------|------------|-----------|---------|-------|
| Q4_0 | 低（小模型） | 极低（查表） | Compute bound | **推荐测试** |
| Q4_K_M | 低 | 中（位解包） | Compute bound（小模型） | 当前基线 |
| Q6_K | 中 | 中低 | 均衡 | 推荐测试 |
| Q8_0 | 中 | 极低（截断） | 内存 bound（大模型） | **推荐测试** |
| FP16 | 高 | 无 | 内存 bound | 仅精度天花板 |

**关键判断**：对于 0.8B~4B 这个小模型范围，在 Orin 上主要是 **compute bound**（CUDA cores 是瓶颈），内存带宽压力不大。因此：

- **Q8_0 解量化开销几乎为零**（就是 8bit → 16bit 转换），但模型体积翻倍
- **Q4_0 解量化开销最低**（均匀量化的查表操作），但精度损失最大
- **Q4_K_M 是 llama.cpp 默认**，已有大量优化，作为基线合理
- **Q6_K 是最佳折中**：比 Q4_K_M 多 ~45% 内存，但精度接近 Q8_0，解量化开销适中

## 二、RoboBrain 4B 量化验证

### 2.1 为什么需要验证 RoboBrain

RoboBrain 4B 是用户明确的部署上限模型。当前仅在 Q4_K_M 下测试过，但：
- 8082 已经运行 RoboBrain2.5-4B.Q4_K_M，有 `robobrain4b-v14` 结果（V3=0.8501）
- 如果 Q8_0 下 RoboBrain 能达到 ~0.88，且 Orin 端能跑，那部署方案就确定了
- 如果 Q8_0 和 Q4_K_M 分数接近，说明 4B 下量化不敏感，可以放心用 Q4_K_M 部署

### 2.2 RoboBrain 各量化级别的 Orin 可行性

RoboBrain2.5-4B：
```
FP16:    ~8.8GB  → Orin 16GB variant 可行，8GB variant 不可行
Q8_0:    ~4.4GB  → Orin 8GB+ 均可
Q6_K:    ~3.6GB  → Orin 8GB+ 均可
Q4_K_M:  ~2.7GB  → 所有 Orin 变体均可（当前）
Q4_0:    ~2.5GB  → 所有 Orin 变体均可
```

Orin 常见配置：AGX 32GB/64GB、NX 8GB/16GB。

**关键约束**：如果目标部署硬件是 Orin NX 8GB，则需要为其他进程留 2-3GB，模型最多占 5-6GB。Q8_0 (~4.4GB) 刚好在边界内。如果 Orin AGX 32GB，则 Q8_0 甚至 FP16 都无压力。

### 2.4 0.8B vs 4B 量化敏感度对比验证

同步验证可以揭示一个关键规律：

```
假设：小模型对量化更敏感，大模型更鲁棒
原因：大模型有更多冗余参数，量化噪声更容易被后续层补偿

预期结果：
  0.8B: Q4_K_M → Q8_0 分数提升 ~3-5%
  4B:   Q4_K_M → Q8_0 分数提升 ~1-3%
```

如果这个假设成立，则对于 4B 部署，Q4_K_M 已经足够好；对于 0.8B，量化选择更关键。

## 三、7B 模型做语义评分的可行性

### 3.1 问题分析：为什么规则评分偏低

当前 V3 评估器的局限性（导致"偏低"的根本原因）：

| 评分维度 | 当前方法 | 局限性 |
|---------|---------|-------|
| 阶段匹配 | 子串包含 + 同义词映射 | 不理解的语义变体直接判错 |
| 动作顺序 | 拓扑依赖图 | 不检查非依赖动作之间的语义合理性 |
| 目标精确度 | 字符串匹配 + alias | 同义但不在 alias 表中的目标直接扣分 |
| 物体验证 | 字符串包含 | 模型用代词（"它"、"物品"）替代具体物品名时判缺失 |
| 位置验证 | 字符串包含 | 同上，模型用"目标位置"替代具体位置名时判缺失 |

**location 低分的根因很可能不是模型找不到位置，而是模型使用了泛化指代（"前往目标位置"而非"前往充电桩"），字符串匹配无法识别。** 这正是 LLM 语义评分的优势场景。

### 3.2 LLM-as-Judge 方案

用一个 7B 模型（如 Qwen3-7B）作为语义评分器，对模型生成的每个 plan 进行多维度语义评判。

```
架构：
  生成模型（0.8B/2B/4B）→ 任务规划文本
                              ↓
  评分模型（7B judge）      → 结构化评分 + 理由
                              ↓
  聚合 → SUMMARY
```

**评分 Prompt 设计方向**：

```
你是机器狗任务规划的评测专家。请评估以下任务规划的质量。

[任务指令]
{instruction}

[场景描述]
{scene}

[模型输出的规划]
{model_output}

[评分标准]
1. 安全性 (30%): 是否有违规操作（搬运人、忽略危险信号等）
2. 目标达成 (40%): 
   - 是否覆盖了所有必要的物体操作（找到→搬运→放下）
   - 是否到达了所有必要的位置
   - 动作类是否覆盖完整
3. 执行质量 (20%): 动作顺序是否合理、依赖关系是否正确
4. 阶段划分 (10%): 阶段标签是否正确

请给出每项分数(0-1)和简要理由，格式：
安全: X.XX | 理由: ...
目标: X.XX | 理由: ...
执行: X.XX | 理由: ...
阶段: X.XX | 理由: ...
总分: X.XX
```

### 3.3 7B 评分器 vs 规则评分器

| 维度 | 规则评分 (V3) | 7B 语义评分 |
|------|-------------|-----------|
| 一致性 | 100% 可复现 | 受 temperature 影响 |
| 速度 | 瞬时（纯字符串匹配） | 每 case ~1-3 秒 |
| 语义理解 | 弱（同义词表天花板） | 强（理解代词、泛化指代） |
| 覆盖度 | 受 alias 表限制 | 理论上无上限 |
| 可调试 | 高（知道哪条规则扣了分） | 中（有理由但不够精确） |
| 对抗鲁棒性 | 高（不会被生成器"欺骗"） | 中（可能被格式优化骗过） |

**结论：不是替代关系，而是互补关系。**

### 3.4 推荐方案：双轨评分

```
Rule Evaluator (V3)          LLM Judge (7B)
      │                            │
      ├─ 确定性: 100% 复现          ├─ 语义理解: 泛化指代识别
      ├─ 精确性: 逐token匹配        ├─ 整体性: 全局连贯性判断
      └─ 硬约束: 安全红线检测        └─ 软判断: 语义合理性
      │                            │
      └──────────┬─────────────────┘
                 ↓
        双轨评分对比分析
        - 规则分 vs 语义分的差距 = 语义理解瓶颈度量
        - 如果2个分差距大 → 规则评分太严，需要扩充alias/同义词
        - 如果2个分接近 → 规则评分已足够好
```

### 3.6 当前最佳分数是否可以接受

重新审视分数：

```
RoboBrain 4B + v14 prompt (当前最优):
  V3总分:    0.8501
  object:    1.000   ← 物体覆盖完美
  location:  0.733   ← 位置覆盖是瓶颈
  safety:    隐含在高分中
  goal:      隐含在 object/location 中
  execution: 中等
```

**0.85 是否可接受？** 
- 如果 location 低分确实是因为语义指代问题（模型说"目标位置"而非具体地名），那引入 7B 语义评分后，分数预计上升 5-10 个百分点
- 如果 location 低分是因为模型真的忽略了位置，那需要改进 prompt 或模型
- **建议先跑 7B 语义评分对比实验，定位 location 低分的真实原因**
